My Agent Workflow: A Practical Playbook

2026-09-21

AI agents are fast but chaotic. Left alone, an agent will happily build the wrong thing at impressive speed. So I run every agent-built project through the same five-stage workflow: environment setup, product design, technical design, implementation, and human verification. Each stage is a gate — nothing moves forward until the gate is passed.

This isn't theory. I used exactly this workflow to design and build Readyday — a daily body-readiness score for iPhone and Apple Watch, one number with the reasons behind it — from an empty repo to release prep in a single day of building. Here's the playbook, with Readyday as the worked example.

Step 1 — Environment setup: Git + CLAUDE.md

Before the agent writes a single line of code, I set up two things: a Git repository, so every change is tracked and reversible, and a CLAUDE.md file at the repo root — the agent's standing instructions. Readyday's entire file is two bullets:

After every completed change, you must create a corresponding Git commit. After every change, you must write or update the relevant tests, and all tests must pass before delivering the work.

That's the whole constitution. It's the highest-leverage artifact in the workflow: written once, it governed every one of the dozens of commits that followed. Prompts are per-task; this file is permanent.

Step 2 — Product design: the proposal is the gate

Next the agent wrote docs/PLAN.md: research on the problem space, the target user, and — most importantly — the cut line. For Readyday the scope decision was one sentence. Everything else was parked in V2.md, explicitly deferred, not forgotten.

v1 is the glance — one number, one word, one sentence, plus three lines saying why.

The proposal is a decision tool, not a deliverable. Naming, bundle IDs, the competitive research — all settled here, before any engineering. If the glance hadn't convinced me, the idea would have died here, cheaply, instead of after a week of code.

Step 3 — Technical design: what, why, how — separated

Only after the product direction was settled did the technical design happen, split across three documents with a strict division of labor. ALGORITHM.md is the maths. DESIGN-SYSTEM.md is the look — six visual laws, each traced to a line in the algorithm. IMPLEMENTATION.md is the how, and it states its own precedence rule:

PLAN.md is the what and why, ALGORITHM.md is the maths, DESIGN-SYSTEM.md is the look. Where this file and those disagree, they win and this one is wrong.

That precedence rule is the whole point of this stage. I reviewed the design myself — it's the cheapest place in the process to catch mistakes. A wrong call here multiplies into days of wrong code later. My rule: if I can't explain the technical proposal back in my own words, it's not ready for implementation.

Step 4 — Implementation: small commits, tested relentlessly

Then the agent built: four Swift packages (scoring engine, HealthKit data, UI kit, local store), the iPhone app, the watch app, widgets, and complications — in small increments, one commit per change, exactly as CLAUDE.md demanded. The commit log tells the story: Add the implementation plan and ReadinessCore: 28 tests green, Build the Today screen, and fix the two defects it exposed.

Tests weren't an afterthought; the scoring engine has persona-based calibration tests and the data layer has fixture-backed tests. The self-test gate held: nothing was delivered to me until the suite was green.

Step 5 — Human verification: the skeptic's job

The last gate is always human, and it's always me. The agent is optimistic by nature — it wants to tell you it's done. My job is to be the skeptic it can't be. On Readyday that meant real product calls: making morning the default theme, drawing the MVP1 cut-line table, and deferring all of StoreKit with explicit reasoning:

You cannot learn what people will pay for before you know whether they open it daily.

Nothing merges, deploys, or ships without this. I check three things: does it do what the proposal promised, would I ship it to a real user, and did every stage of this workflow actually happen.

The day, hour by hour

Readyday went from empty repo to release prep in a single day. The commit log is the workflow in motion — design, build, test, verify, repeat:

The part the diagram doesn't show: the loop

On paper the workflow is a straight line. In practice it loops. Readyday's final commit of the day was Prepare the release, and fix what a Release build exposed — verification feeding straight back into implementation. When human review finds a problem, work goes back: usually to implementation, sometimes to technical design if the approach was wrong, occasionally to product design if the plan lied. The stages don't change; the path through them just isn't always forward.

The checklist

  • Environment: repo initialized, agent constitution (CLAUDE.md / AGENTS.md) written
  • Product design: proposal written, cut line drawn, the rest parked in v2
  • Technical design: what / why / how separated, precedence rules stated, reviewed by a human
  • Implementation: small commits, tests with every change, suite green before handoff
  • Human verification: does it match the proposal, would you ship it, did every stage happen

That's the whole playbook: set up the environment once, design twice (product, then technical), let the agent build and test itself, and keep the final judgment human. It won't make the agent brilliant, but it will keep it honest — and honest is what ships. In Readyday's case, honest shipped in a day.
