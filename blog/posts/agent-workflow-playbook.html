My Agent Workflow: A Practical Playbook

2026-09-21

AI agents are fast but chaotic. Left alone, an agent will happily build the wrong thing at impressive speed. So I run every agent-built project through the same five-stage workflow: environment setup, product design, technical design, implementation, and human verification. Each stage is a gate — nothing moves forward until the gate is passed.

This is the story of that workflow in action. Last week I built Readyday — a daily body-readiness score for iPhone and Apple Watch, one number with the reasons behind it — entirely in side-hustle hours: my commute, early mornings, and evenings around my day job. Research on Thursday, design on Sunday afternoon, then build sessions stolen between Sunday evening and Tuesday morning. Empty repo to release prep, no workday hours touched. Here's how each stage carried its weight.

Step 1 — Environment setup: the constitution comes first

Thursday evening, two commits, and the repo existed. The first added the research notes. The second added CLAUDE.md — the agent's standing instructions. The entire file is two bullets:

  • After every completed change, you must create a corresponding Git commit.
  • After every change, you must write or update the relevant tests, and all tests must pass before delivering the work.

Written once, it governed every commit that followed — including all the ones I never watched happen, because I was on a train. That's the point: the constitution works when I'm not there.

Step 2 — Product design: Sunday afternoon, the cut line

Sunday afternoon I sat down and did the product thinking myself, with the agent as a scribe. The project got renamed from Headroom to Readyday, the bundle ID got registered, and docs/PLAN.md took shape: the readiness algorithm spec, the band names (Rest / Easy / Train / Push), the business model (freemium with a 7-day history wall) — and the cut line, one sentence that decided the whole release:

v1 is the glance — one number, one word, one sentence, plus three lines saying why.

Everything else went into V2.md: explicitly deferred, not forgotten. The proposal is a decision tool, not a deliverable. If the glance hadn't convinced me, the idea would have died on Sunday afternoon, cheaply, instead of after a week of code.

Step 3 — Technical design: Sunday evening, what vs. why vs. how

Sunday evening the technical design landed, split across three documents with a strict division of labor. ALGORITHM.md is the maths. DESIGN-SYSTEM.md is the look — six visual laws, each traced to a line in the algorithm, with design-law tests to enforce them. IMPLEMENTATION.md is the how, and it states its own precedence rule:

PLAN.md is the what and why, ALGORITHM.md is the maths, DESIGN-SYSTEM.md is the look. Where this file and those disagree, they win and this one is wrong.

I reviewed it myself before bed — the cheapest place in the process to catch mistakes. A wrong call here multiplies into days of wrong code. My rule: if I can't explain the technical proposal back in my own words, it's not ready for implementation.

Step 4 — Implementation: the agent builds while I commute

This is where the workflow paid for itself. Monday morning I opened the laptop before leaving, gave the agent the implementation plan, and it built while I commuted: the scoring engine ReadinessCore with 28 tests green, then the Today screen, real HealthKit data, the App Group store, the Home Screen widget, the watch app and its complication. Small increments, one commit per change, exactly as the constitution demanded — Build the Today screen, and fix the two defects it exposed.

Tests weren't an afterthought; the scoring engine has persona-based calibration tests and the data layer has fixture-backed tests. The self-test gate held: nothing was delivered to me until the suite was green. I checked in between sessions; the docs told me exactly where things stood. No status meetings with my own agent.

Step 5 — Human verification: the skeptic's job

The last gate is always human, and it's always me. The agent is optimistic by nature — it wants to tell you it's done. My job is to be the skeptic it can't be. On Readyday that meant real product calls: making morning the default theme, drawing the MVP1 cut-line table, and deferring all of StoreKit with explicit reasoning:

You cannot learn what people will pay for before you know whether they open it daily.

Nothing merges, deploys, or ships without this. I check three things: does it do what the proposal promised, would I ship it to a real user, and did every stage of this workflow actually happen.

The build, session by session

No clock times — this wasn't a workday. It was stolen hours, and the workflow is what made stolen hours enough:

  • Thu eveningResearch notes and the constitution — the repo is born
  • Sun afternoonRenamed Headroom → Readyday; algorithm spec; scope cut to the glance
  • Sun eveningDesign system with six laws; first UI commits
  • Mon early morningPolish pass before leaving for the office
  • Mon commuteImplementation plan; scoring engine — 28 tests green
  • Mon middayToday screen, live health data, watch app and complication
  • Mon eveningRelease prep; the release build exposes issues, fixed in the same session
  • Tue early morningFinal fixes, README — ready for TestFlight

The part the diagram doesn't show: the loop

On paper the workflow is a straight line. In practice it loops. Readyday's Monday-evening session was Prepare the release, and fix what a Release build exposed — verification feeding straight back into implementation. When human review finds a problem, work goes back: usually to implementation, sometimes to technical design if the approach was wrong, occasionally to product design if the plan lied. The stages don't change; the path through them just isn't always forward.

Why this works for a side hustle

Here's the thing I didn't expect: the staged documents turned out to be a handoff system. When your build time comes in 40-minute commute slices, you can't afford to re-brief your agent every session. I never did. The plan said what to build, the design docs said how, the commit log said what was already done. Each session started with the agent reading the docs and continuing — no context lost between my train rides.

The checklist

  • Environment: repo initialized, agent constitution (CLAUDE.md / AGENTS.md) written
  • Product design: proposal written, cut line drawn, the rest parked in v2
  • Technical design: what / why / how separated, precedence rules stated, reviewed by a human
  • Implementation: small commits, tests with every change, suite green before handoff
  • Human verification: does it match the proposal, would you ship it, did every stage happen

That's the whole playbook: set up the environment once, design twice (product, then technical), let the agent build and test itself, and keep the final judgment human. It won't make the agent brilliant, but it will keep it honest — and honest is what ships. In Readyday's case, honest shipped in stolen hours.
