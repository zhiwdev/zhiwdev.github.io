My Agent Workflow: A Practical Playbook

2026-09-21

AI agents are fast but chaotic. Left alone, an agent will happily build the wrong thing at impressive speed. So I run every agent-built project through the same five-stage workflow: environment setup, product design, technical design, implementation, and human verification. Each stage is a gate — nothing moves forward until the gate is passed. Here is exactly how I do it.

Step 1 — Environment setup: Git + AGENTS.md

Before the agent writes a single line of code, I set up two things. First, a Git repository, so every change is tracked and reversible. Second, an AGENTS.md file at the repo root — the agent's standing instructions. Mine covers project conventions, coding standards, and most importantly the definition of done: what "finished" means, including my rule that nothing is announced as done until tests pass and the live result is verified.

This file is the highest-leverage artifact in the whole workflow. You write it once, and it governs every session after that. Prompts are per-task; AGENTS.md is the constitution.

Step 2 — Product design: proposal, then demo

Next I have the agent write a product proposal: the problem, the target user, what is in scope, and — just as important — what is explicitly out of scope. Then, before any real engineering, it builds a demo: something I can click through and react to.

The demo is a decision tool, not a deliverable. If it doesn't convince me, the idea dies here, cheaply. Killing a bad idea at the demo stage costs an hour; killing it after implementation costs a week.

Step 3 — Technical design: the technical proposal

Only after the product direction is settled does the agent write a technical proposal: architecture, data model, key dependencies, and the main trade-offs. I review this myself, carefully. This is the cheapest place in the entire process to catch mistakes — a wrong call here multiplies into days of wrong code later.

My rule: if I can't explain the technical proposal back in my own words, it's not ready for implementation.

Step 4 — Implementation: code, then AI self-test

Now the agent writes code, in small increments with commits along the way so nothing is ever more than a step or two from a working state. When it believes the work is done, it runs an AI self-test: the test suite, plus a check against the acceptance criteria from the product and technical proposals.

The self-test is a real gate, not theater. If tests fail or the build doesn't match the proposal, the agent fixes it and re-tests — I don't get involved until it passes its own checks.

Step 5 — Human verification: the final gate

The last gate is always human, and it's always me. I check three things: does it do what the product proposal promised, would I ship it to a real user, and did every step of this workflow actually happen. Nothing merges, deploys, or ships without this.

The agent is optimistic by nature — it wants to tell you it's done. My job at this stage is to be the skeptic it can't be.

The part the diagram doesn't show: the loop

On paper the workflow is a straight line. In practice it loops. When human verification finds a problem, work goes back — usually to implementation, sometimes to technical design if the approach was wrong, occasionally all the way back to product design if the demo lied. The stages don't change; the path through them just isn't always forward.

That's the whole playbook: set up the environment once, design twice (product, then technical), let the agent build and test itself, and keep the final judgment human. It won't make the agent brilliant, but it will keep it honest — and honest is what ships.
