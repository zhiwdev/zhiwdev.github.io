The Boring Secret to Building with AI Agents

2026-09-21

The boring secret is paperwork. I don't mean clever prompts or a better model. I mean plain documents, written in a fixed order, that the agent reads before it touches the code.

I learned this building ReadyDay, a small wellness app for iPhone and Apple Watch that gives you one readiness number each morning and the reasons behind it. I built it on my own time, Thursday to Tuesday, in evening and weekend sessions: empty repo to a TestFlight build. Here is exactly how it went, stage by stage.

Step 1 — Environment: two rules in CLAUDE.md

The repo started with two commits: my research notes, and a CLAUDE.md file with the agent's standing instructions. The whole file is two rules:

  • After every completed change, you must create a corresponding Git commit.
  • After every change, you must write or update the relevant tests, and all tests must pass before delivering the work.

That's it. These two rules keep every change tracked and tested. They don't stop the agent from building the wrong thing, though. The next two steps handle that.

Step 2 — Product design: draw the cut line

On Sunday afternoon I did the product thinking myself and let the agent take notes. Out of that came PLAN.md: the problem, the readiness bands (Rest / Easy / Train / Push), the business model, and one sentence that decided what the first release would be:

v1 is the glance — one number, one word, one sentence, plus three lines saying why.

Everything else went into V2.md, deferred on purpose rather than forgotten. The plan is a decision tool, not a deliverable. If the one-screen version hadn't convinced me on paper, the idea would have died that afternoon. Killing an idea at this stage costs an hour; killing it after implementation costs a week.

Step 3 — Technical design: the math, the look, the build plan

On Sunday evening I split the technical design into three files. ALGORITHM.md has the math. DESIGN-SYSTEM.md has six visual rules, each tied back to a line in the algorithm and checked by tests. IMPLEMENTATION.md has the build plan, and it says which file wins when they disagree:

PLAN.md is the what and why, ALGORITHM.md is the maths, DESIGN-SYSTEM.md is the look. Where this file and those disagree, they win and this one is wrong.

That rule looks fussy, but an agent that finds two documents in conflict will pick one of them, and I want that decided in advance. I reviewed the whole design before any code was written, because this is the cheapest place to catch a mistake. My rule: if I can't explain the approach back in my own words, it's not ready to build.

Step 4 — Implementation: small steps, tests every time

On Monday the agent built, in small steps with one commit per change. First came the scoring engine, ReadinessCore, with 28 tests passing. Then the main screen, live Apple Health data, a Home Screen widget, and the watch app. The scoring engine has persona-based calibration tests, and the data layer runs against fixture data. Nothing came back to me until the whole suite passed.

One warning. Passing tests only tell you the code does what the tests say. When the agent writes both, the same blind spot can sit in both places. So I never treat a green suite as the finish line.

Step 5 — Human verification: the skeptic's job

The last gate is always human, and it's always me. The agent is optimistic by nature; it wants to tell you it's done. My job is to be the skeptic. On ReadyDay that meant calls no test could make: which theme ships as the default, where exactly the first-release cut falls, and pushing in-app purchases out of v1 entirely, for this reason:

You cannot learn what people will pay for before you know whether they open it daily.

I check three things. Does it do what the plan promised? Would I put it in front of a real user? Did every stage actually happen?

What surprised me: the documents are a handoff system

I build in short sessions, some of them forty minutes long. The expensive part of a short session is getting back up to speed, for me and for the agent. I never had to re-brief it. The plan said what to build, the design docs said how, and the commit history said what was already done. Each session, the agent read those and kept going.

The same is true for people. Hand those files to a colleague and they could pick up where the agent left off.

It loops

On paper this is a straight line. In practice it loops. On Monday evening the release build turned up problems, and work went back to implementation. Sometimes it goes back further: to technical design if the approach was wrong, or to product design if the plan was. The stages don't change; the path through them just isn't always forward.

Why I think this carries over to analytics teams

I trained as an epidemiologist, and most of this is old analytics discipline with a new collaborator.

Plan before you touch the data. In epidemiology you write the analysis plan first, so the results can't quietly change the question. The risk with an agent is different (building the wrong thing rather than fishing for a significant result), but the habit is the same.

Keep every change traceable. One commit per change, with its tests, means anyone can see what changed and why. That's what makes the work reviewable.

Keep the decision with a person. An agent can produce a forecast or a targeting list. It can't own what happens next. Someone with a name signs off.

Write for the next reader. The files that let an agent pick up where it left off will do the same for a new analyst.

What this doesn't prove

This is one project, built by one person, from scratch. I didn't build the same app without the process to compare, so I can't say the process is why it shipped. Teams also deal with things this project never had to: shared data, validation, formal review. Treat it as a worked example. I'll keep using it and write up where it breaks.

The checklist

  • Environment: repo set up, standing instructions (CLAUDE.md / AGENTS.md) written
  • Product design: plan written, cut line drawn, everything else parked for v2
  • Technical design: math, look, and build plan in separate files; precedence stated; reviewed by a person
  • Implementation: small commits, tests with every change, full suite passing before handoff
  • Human verification: matches the plan, fit for a real user, no stage skipped
  • Loop: when review fails, send the work back to the stage where the mistake started

That's the whole playbook: set up the environment once, design twice (product, then technical), let the agent build and test itself, and keep the final judgment human. It won't make the agent brilliant. It will keep it honest, and honest is what ships.

ReadyDay is a personal project, built on my own time and equipment. It's a general wellness app: it doesn't diagnose, treat, or give medical advice. All views here are my own and don't represent my employer.
